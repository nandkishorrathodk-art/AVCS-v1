# AVCS System 1 clean-room training pipeline

## State and scope

This is a separate, synthetic-only data path for a possible random-initialization System 1 candidate. It does not alter the legacy trainer, frozen checkpoint, prior candidate weights, legacy datasets, or demonstrations. It does not train System 2, temporal motion behavior, or motor-control behavior.

The generated corpus is **not rights-cleared by default**. Its manifest and every sample carry `PENDING_OWNER_ATTESTATION`. Training fails before model construction unless the project owner completes [CLEANROOM_DATA_RIGHTS_ATTESTATION.md](./CLEANROOM_DATA_RIGHTS_ATTESTATION.md) for the exact `manifest.json` SHA-256 and supplies the required review evidence. Repository access or a source-code license is not that approval.

The human-readable attestation alone is not approval. The training/evaluation gate additionally requires a signed permission payload, a separate trusted Ed25519 public-key configuration, and the SHA-256 pin for that configuration supplied independently through a trusted operator channel. The signed payload must decide `internal_training`, `commercial_inference`, `public_weight_redistribution`, and `source_dataset_redistribution` as `GRANTED` or `DENIED`; unresolved/blank values are rejected. Training requires `internal_training: GRANTED`; a denial for another permission does not authorize that activity.

The default corpus (64 train, 16 validation, 16 held-out, and 16 negative frames) is a pipeline-validation corpus, not a statistically adequate benchmark or evidence of real-screen accuracy. It yields four generated queries per positive frame and one absent-target query per frame. It intentionally contains only renderer-produced fictional UI.

## Generator and validation

From the repository root in PowerShell:

```powershell
$PYTHON = ".venv\Scripts\python.exe"
& $PYTHON -m avcs.dataset.cleanroom_v1.generator `
  --output-dir "datasets\cleanroom_system1_v1" `
  --seed 20261018
& $PYTHON -m avcs.dataset.cleanroom_v1.generator `
  --output-dir "datasets\cleanroom_system1_v1" `
  --validate-only
```

The generator refuses to write into a non-empty destination. It uses first-party Pillow drawing primitives and the project-authored 5×7 glyph table only; it has no system-font fallback and does not read legacy images, masks, annotations, demonstrations, or weights. The generated manifest records the renderer, glyph table, and input-builder source hashes, Pillow/Python versions, per-file hashes, split seeds, layout families, labels, annotation schema, provenance and pending rights status.

Train, validation, held-out, and negative-test layout families and seed ranges are disjoint. The validator checks file digests, image format and dimensions, annotation references, supported labels and kinds, box/point bounds, nonempty splits, unique seeds and frame IDs, split-level hash collisions, and family leakage. Changing pipeline source after generation invalidates the recorded source hashes; regenerate and re-attest rather than editing a manifest to hide the discrepancy.

## Lockfile environment verification

Use a separate environment and keep the lockfile unchanged:

```powershell
$env:UV_PROJECT_ENVIRONMENT = "$env:TEMP\avcs-system1-cleanroom-locked"
uv sync --locked --extra dev --no-install-project --python 3.14
& "$env:UV_PROJECT_ENVIRONMENT\Scripts\python.exe" -c "import sys, torch, numpy, PIL; print(sys.version); print(torch.__version__, numpy.__version__, PIL.__version__)"
& "$env:UV_PROJECT_ENVIRONMENT\Scripts\python.exe" -m pytest -q tests\test_cleanroom_system1_v1.py tests\test_cleanroom_rights_hardening.py
```

The project lock is version/marker-specific. Record the actual environment output; the manifest records the environment that generated it. The original 112-frame corpus records Pillow 13.0.0, while the current lock resolves Pillow 12.3.0 for Python 3.14, so that corpus was **not** generated by the current locked environment. Do not rewrite or silently regenerate it. Compare any lock-environment regeneration in two new, empty output directories and treat any output change as a new corpus revision requiring its own manifest digest and owner review.

## Rights gate and training

Review the generated manifest hash:

```powershell
Get-FileHash "datasets\cleanroom_system1_v1\manifest.json" -Algorithm SHA256
```

An authorized owner must complete the attestation template, reference evidence for contributions and dependency licenses, affirm every required statement, enter that exact digest, and explicitly state that no blockers remain. Do not fill it on the owner's behalf.

Only after that approval, run the isolated trainer:

```powershell
& $PYTHON -m avcs.training.train_system1_clean_v1 `
  --manifest "datasets\cleanroom_system1_v1\manifest.json" `
  --attestation "docs\CLEANROOM_DATA_RIGHTS_ATTESTATION.md" `
  --approval "docs\CLEANROOM_RIGHTS_APPROVAL.json" `
  --trust-config "$env:AVCS_RIGHTS_TRUST_CONFIG" `
  --output "runs\weights\clean_lineage_candidates\avcs_system1_clean_v1.pt" `
  --epochs 10 --batch-size 4 --learning-rate 0.0003 --seed 20261018
```

The project does not contain an owner key, signed approval, or trusted-key configuration. The owner/operator must provide them through approved channels; do not generate keys or signatures for the owner. Set `AVCS_RIGHTS_TRUST_CONFIG_SHA256` in the protected trainer environment from the approved out-of-band value; the trainer does not accept this pin as an ordinary command-line argument or read it from the approval document. The trust configuration is accepted only if its file hash equals that pin. A valid signature proves only that the trusted private key signed the exact manifest digest and permission set; it does not establish that the owner's legal claims are true or that the owner has authority.

The trainer constructs `AVCSSystem1V1` directly after seeding Python, NumPy, and PyTorch, temporarily makes any `torch.load` call fail during construction, checks that all model parameters are trainable, and fingerprints the initialized tensors. It cannot write under the frozen baseline or the legacy `runs\weights\candidates` directory, refuses existing outputs, and does not load a prior checkpoint or optimizer state. The training metadata and sidecar record the initialization fingerprint, exact manifest, signed approval, and trust-config hashes, decisions, configuration, command, dependency versions, source hashes, split counts, per-epoch losses, and output digest.

Proposal, category, grounding/presence, and pixel-word branches receive explicit losses. A first-batch gradient audit requires a finite, nonzero gradient through each trainable proposal, category, grounder, and word-recognition module. The deterministic temporal engine has no learned parameters and is not claimed as trained. Model selection uses validation loss; the two final test splits are excluded from training and model selection.

## Held-out evaluation

After a gated clean candidate exists:

```powershell
& $PYTHON -m avcs.training.evaluate_system1_clean_v1 `
  --checkpoint "runs\weights\clean_lineage_candidates\avcs_system1_clean_v1.pt" `
  --manifest "datasets\cleanroom_system1_v1\manifest.json" `
  --attestation "docs\CLEANROOM_DATA_RIGHTS_ATTESTATION.md" `
  --approval "docs\CLEANROOM_RIGHTS_APPROVAL.json" `
  --trust-config "$env:AVCS_RIGHTS_TRUST_CONFIG" `
  --output "runs\weights\clean_lineage_candidates\avcs_system1_clean_v1.evaluation.json"
```

The evaluator verifies the checkpoint sidecar and lineage, exact dataset and attestation hashes, and reads only the held-out and negative splits for model metrics. It reports interactive-region precision/recall at IoU 0.5, query presence, point-in-target-box success and localization error, known/unknown-word performance, absent-target rejection, CPU latency, throughput, and process peak memory. Accuracy metrics are explicitly synthetic; they must not be presented as results on real desktop screens.

## Explicit limitations and release gate

- The bitmap renderer uses a narrow uppercase ASCII glyph set and a small, declared control vocabulary. It is not representative of installed desktop applications, realistic typography, localization, accessibility metadata, or arbitrary screen content.
- The corpus is small and renderer-defined. Training on it can validate plumbing and gradient flow, not support broad capability or deployment claims.
- Pillow is needed by the generator; training/evaluation also require the declared NumPy, PyTorch, and `cryptography` dependencies. Their licenses and bundled notices must be reviewed and documented by the authorized owner.
- A generated manifest is not an attestation, and a synthetic clean lineage does not establish sufficient evaluation or grant weight-distribution permission.
- No existing model is overwritten. No checkpoint is produced while rights remain pending. No weights are uploaded, no endpoint is enabled, and no GitHub repository is changed by this pipeline.
